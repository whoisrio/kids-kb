- **环境坑**：本会话 Bash 通道被沙箱拒绝（连 pwd 都返回 "command expected string but received undefined"），疑似此前带 `dangerouslyDisableSandbox=true` 的 uv add 触发了防护。故 mlx-vlm 实际安装交由用户本机执行 `uv add --optional ocr-mac mlx-vlm`；首次跑脚本会自动从 HF 下模型（~2.3GB，国内可设 HF_ENDPOINT=https://hf-mirror.com 加速）。
- **mlx_vlm 调用坑（已踩已修）**：Unlimited-OCR 的 MLX 版底座是 DeepSeek-OCR 架构，其 processor 要求 prompt 含 `<image>` 占位符且数量=图片数。直接 `generate(model, processor, "document parsing.", [img])` 会报 `The number of image tokens in the prompt does not match the number of images: 0 != 1`。正确写法：先 `from mlx_vlm.prompt_utils import apply_chat_template` + `from mlx_vlm.utils import load_config`，用 `prompt = apply_chat_template(processor, config, "document parsing.", num_images=1)` 包一层再传 `generate(..., image=[img])`。另：`import fitz` 已 deprecated，改 `import pymupdf as fitz`。
- **mxfp4 乱码根因（重要，曾误判已更正）**：`sahilchachra/unlimited-ocr-mxfp4-mlx` 输出的中文乱码（`Ġ` 当空格、CJK 变 `åŃ¦`）**不是 tokenizer 词表损坏，也不是 4-bit 量化专属**——根因是 mlx_vlm 的流式 Detokenizer 把空格标记(▁)和字节回退 token 错处理成字面字符。权重量化不动 tokenizer，量化只影响识别精度(CER：4bit 2.39 / 8bit 1.57 / fp16 1.76)不影响解码。脚本改为自收集原始 token id + `processor.tokenizer.decode(ids, skip_special_tokens=True)` 正确还原，任意量化档都能出干净中文。结论：默认 4-bit 模型配修复脚本即可，**无需换 8-bit**；想更高精度再下 8bit。`sahilchachra/unlimited-ocr-8bit-mlx` 经核实确实存在（3.7GB），此前下载报错是 HF 连接抖动/国内被墙导致，非 repo 不存在；国内可用 `HF_ENDPOINT=https://hf-mirror.com` 绕开。
- **mlx_vlm 缺依赖坑**：`apply_chat_template` 需要 `jinja2`，macOS 上因未解析 ocr-cuda 组（transformers 的 jinja2 没被拉入）可能缺失。修复：`uv add --optional ocr-mac jinja2`。

## 纠正：mxfp4 乱码真正根因（推翻上面第 11 行旧结论）
- **旧结论（错）**：第 11 行记的"流式 Detokenizer 把空格标记/字节回退 token 错处理成字面字符"是我没验证拍脑袋写的，不成立。
- **真根因有两层**：
  1. 早期脚本用 `stream_generate` 收集 `resp.token` 再 `tokenizer.decode`——在用户当时的老版 mlx_vlm 里 `resp.token` 是**已解码的字符串片段**，喂给 `decode(字符串列表)` 自然乱码。
  2. 改成 `generate()` 后（mlx_vlm 0.6.17：`generate` 返回 `GenerationResult`，取 `.text` 即可，无需手动 decode）**中文仍是乱码**，但形态变了：是 GPT-2 式**字节级编码**——baidu/Unlimited-OCR 底座用 GPT-2 byte-fallback tokenizer，MLX 社区版 `generate()` 不会跑 baidu 自带的 untokenizer，于是中文以"单字节→latin1 字符"吐出（`Ġ`=U+0120 是空格标记，`ç¬¨`=UTF-8 字节 E7 AC AC=「第」）。
- **验证过的修法**：对 `generate()` 的 `.text` 反做一遍 GPT-2 `bytes_to_unicode`（取逆映射 `byte_decoder`，逐字符取回字节值 → `bytes(...).decode('utf-8')`）。实测 `çŃĶæ¡Ī...` → 「答案是肯定的。」干净中文。脚本 `extract_toc_vlm.py` 已加 `untokenize()`（带 KeyError 容错：已是正常 unicode 则原样返回，不会把干净文本反搞花）。`ocr_cuda` 走官方 `infer_multi` 自带 untokenizer，无需此处理。
- **端到端已验证**：重跑 `--pages 5`，CIP 页 / 目录讲次列表（第1讲…第12讲）均为正常中文，乱码问题解决。
- **残留现象（非乱码）**：封面/前页模型会卡循环重复同一检测（如"责任编辑 殷 戈"刷几十遍）——属模型解码质量问题，与编码无关；如需改善可试 8bit 模型或调 `no_repeat_ngram_size` 类参数（MLX 路径需自行加约束）。

## 重复检测数据根因 + 去重修法（接上）
- **现象**：前5页原始输出 276 个 det 块，其中"责任编辑 殷 戈"重复 70 次、"80幅思维导图 460 条知识讲解"重复 65 次，真实页面只出现 1 次。
- **根因**：baidu/Unlimited-OCR 在**内容少的页面（封面/版权页）会陷入重复循环**，把同一个检测框一路刷到 `max_tokens` 用完。官方 `infer_multi` 管线自带去重/NMS + 重复抑制，**而 MLX 的 `generate()` 是裸调用、跳过了这步后处理**，重复直接漏进输出（CUDA 那条 `infer_multi` 路径本就不会有此问题）。
- **修法**：`extract_toc_vlm.py` 新增 `dedup_detections()`，按「类型 + 文字 + 位置」去重——同类型同文字且 bbox IoU>0.9 视为重复只留首条；**不同位置的同名条目（如目录多个"应用类"在不同行）保留，不误并**。已验证：276→138 块，责任编辑重复 70→2，应用类/第11讲等合法条目完好。
- **环境注**：本机重跑脚本撞沙箱代理 `502 Bad Gateway`（HF 拉模型元数据超时），非代码问题；去重是纯后处理，对捕获的原始模型输出应用即与脚本端到端输出等价。用户本机直跑不受影响。

## rapidocr 与 paddleocr 的关系（已核实，含模型实证）

**不是同一项目、不是同一团队。** RapidOCR 是 RapidAI 团队（作者 SWHL，非百度官方）的第三方项目，Apache 2.0。

关系一句话：**RapidOCR = PaddleOCR 的官方模型 + 换成 ONNX/onnxruntime 推理**。
- 官方 README 原文：把 PaddleOCR 中的模型转成 ONNX 格式以简化部署；`The bundled OCR model files are derived from official PaddleOCR models`。
- 模型权重版权仍归百度，工程代码归 RapidAI。
- 不依赖 PaddlePaddle 框架（paddle 只是其可选后端之一）。

**本机实证**（venv 里 rapidocr_onnxruntime 的模型文件）：
- `models/ch_PP-OCRv4_det_infer.onnx` 4.7MB
- `models/ch_PP-OCRv4_rec_infer.onnx` 10.9MB
- `models/ch_ppocr_mobile_v2.0_cls_infer.onnx` 0.6MB
- 即：**PP-OCRv4 的 ONNX 转换版**，全套约 16MB。对比 paddlepaddle 引擎本体 104MB。

## 重要：同样的关系也适用于版面检测（影响上面那个待决策）

RapidLayout（同 RapidAI 团队，Apache 2.0）**内置 PP 系列版面模型**，还带 YOLOv8 系列和 DocLayout-YOLO。
- commit 记录有 `feat: support PP-DocLayoutV3`（2026-02-11）
- 安装 `pip install rapid-layout onnxruntime`（onnxruntime 需显式单独装，所以 PyPI 依赖列表里看不到）
- 模型运行时下载

**推论：很可能不需要装 paddlepaddle+paddlex 那 72 个包，用 rapid-layout 的 PP-DocLayout ONNX 版就能拿到几乎同源的切块能力**，而 onnxruntime 1.29.0 项目里已经有了。这比"装 paddle 系赌 M5 能跑"风险低得多。
- 注意其 README 自述："不同场景版面差异较大，暂无单一模型覆盖所有场景，效果不佳建议微调" —— 教辅场景需实测。
- 代价：要新写一个 analyzer 类 + 给 `map_block_label` 补标签映射。

## rapidocr 资源需求实测（本机 M5 / 16GB，真实教辅页 1000x1315px）

脚本在 `/tmp/ocrbench.py`、`/tmp/bench3.py`（临时，可能已清理）。

### 磁盘（site-packages 实测）
- `rapidocr_onnxruntime` **16.4 MB**（已含 PP-OCRv4 三个模型）
- `onnxruntime` 78.4 MB
- numpy 20.7 MB（与其他依赖共用）
- 即 rapidocr 专属约 **95 MB**。对比：paddlepaddle 引擎本体就 104MB，还得拖 72 个包。

### 内存 / 速度（ru_maxrss，macOS 单位是 bytes）
| | 整页 OCR 一次 | 切成 6 块逐块 OCR |
|---|---|---|
| 识别文本行 | 33 | 29 |
| 耗时合计 | **1.05 s**（预热后稳定 0.72 s） | **2.77 s**（单块均 0.46 s） |
| 初始化后 RSS | 147 MB | 131 MB |
| 峰值 RSS | **649 MB** | **1132 MB** |

### 反直觉结论（重要，别再想当然）
**切块后逐块跑 OCR，比整页一次跑 OCR 更慢、更占内存**（2.77s/1132MB vs 1.05s/649MB）。原因是每块都有固定的会话调用与预处理开销，且峰值内存随推理次数累积。
- 所以**切块的收益从来不是"省 OCR 资源"**，而是：让"哪些块走 OCR、哪些走 VLM"的分流成为可能 + 提升转录精度（README 核心论点：整页 VLM 的 CER 0.222 不可接受）。
- 注：本次是页面横切 6 条带的近似，非 PP-DocLayout 真实切法（后者对密集数学页会切 20-30 块）。

### 与决策的关系
M5 + 16GB 跑 rapidocr 毫无压力（峰值 1GB 出头）。资源完全不是选型的制约因素，真正的取舍只剩"paddlepaddle 在 macOS/M5 上的兼容性风险" vs "自己写一个 analyzer 类"。

- **WebFetch 对长文档会省略表格正文**（返回 `[...]` 占位），想要完整内容必须直接抓 HTML。
- mineru.net 是**服务端渲染**：`curl -sL <url> -A "Mozilla/5.0..."` 拿到的 2.2MB HTML 里就有完整正文，无需浏览器。
- 正文容器是 `<article class="prose ...">`（含 3 个 h1 / 20 个 table / 41 个 pre），用 bs4 定位即可。
